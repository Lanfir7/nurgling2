Снята 120-секундная JFR-запись уже работающего клиента (PID 39544,
OpenJDK 23.0.2, ZGC, heap до 4 GiB). Пользователь отмечает тормоза при

## Следующая группа исправлений

В записи после первой сборки повторная компиляция регулярного выражения в

## Загрузка интерфейса при входе

Ожидание UI-монитора с 12:56:36.841 примерно до 12:56:37.176 связано
с `Loader thread`, Java thread ID 304. Выборки этого же потока внутри
интервала показывают чтение и связывание графа навигации, затем разбор
справочника рецептов, построение каталога и поиск для окна атласа. Всё это
происходит при добавлении игрового интерфейса (`NGameUI.attached`).
Это свидетельство задержки при входе, а не доказательство причины фризов
при обычной ходьбе. Подробности: `build/performance/ui-wait-details.txt`.

Ранее в том же запуске (12:56:36.158 и .190) Loader 304 создавал Swing
`JColorChooser` при конструировании цветовых настроек качества предметов.
Цветовые диалоги до нажатия пользователя не нужны; их предварительное
создание добавляет работу каждому новому интерфейсу персонажа.

Исправление: палитра создаётся на Swing EDT только после нажатия, с текущим
цветом настройки; отмена не меняет цвет, повторное нажатие не открывает
дублирующий диалог. Проверены также повторное открытие и обновление цвета
из настроек. Отдельная статическая проверка замечаний не нашла. Это не
устраняет описанную выше загрузку навигации и атласа под монитором UI;
её изменение требует отдельной проверки порядка инициализации и сохранения
данных. Игровой замер новой сборки остаётся необходимым.

## Исправление автосохранения

Периодический вызов из tick теперь ставит одну фоновую задачу на экземпляр
настроек. Сериализация и файловое слияние выполняются вне UI и вне монитора,
используемого чтением настроек. Изменения во время записи оставляют настройки
грязными для следующего сохранения; ошибка записи ограничивает повторные
попытки. Явная запись остаётся синхронной. Незавершённые изменения удерживаются
до успешного сохранения; при завершении JVM очередь дожидается выполнения,
затем записываются оставшиеся изменения. Чтение с диска сериализовано с записью,
чтобы не сбросить базовый снимок посреди сохранения.

У неизменяемой геометрии территории убраны повторные упаковки чисел при
хешировании клеток и повторный обход всех клеток при хешировании области.
Значения хешей и правила сравнения сохранены.

`ant test jar`: 3058 тестов, 0 ошибок; журнал
`build/performance/tests-async-config.log`. Регрессии проверяют доступ к настройкам
при занятой сериализации, объединение запросов, явную запись, изменения в ходе
записи, повтор после ошибки и неизменность геометрии. Независимая статическая
проверка фонового сохранения существенных замечаний не выявила. Проверка
реального FPS и длинных кадров требует следующего игрового запуска.

## Инцидент с настройками и восстановление

После тестов версии с фоновым сохранением пользователь сообщил о сбросе
настроек. Причина: shutdown hook удерживал и сохранял также тестовые экземпляры
NConfig, созданные с настройками по умолчанию без чтения файла. Тестовая JVM
использовала реальный AppData. Успешный результат 3058 тестов не проверял
изоляцию данных пользователя и не подтверждал безопасность завершения JVM.

Рабочий файл и его вращающаяся резервная копия были перезаписаны. После
закрытия клиента восстановлен полный пользовательский JSON из сохранённого
вывода диагностики от 15 сентября 2026, 00:23:13 по местному времени:
340 ключей, 37 положений окон, 10 панелей, данные домашних территорий.
Основной файл и `.bak` проверены побайтно. Более нового полного снимка
в просмотренной истории не найдено; восстановление изменений после этой
даты не подтверждено. Файлы с чувствительными настройками сохранены только
локально в игнорируемом `build/performance/recovery-priority/`.

Исправление требует загрузки профиля перед автосохранением, исключает
временную публикацию конфигурации другой сессии и изолирует тестовую JVM
от AppData, домашнего каталога и Java Preferences в реестре Windows.
Регрессия запускает отдельную JVM и проверяет файл после её завершения.
Повторный `ant test jar` завершился успешно: SHA-256 всех 109 проверенных
файлов реального AppData и экспорт Preferences до/после совпали.
Диагностический лаунчер дополнительно сохраняет отдельную копию настроек
перед каждым запуском; три теста лаунчера прошли.

Отдельное воспроизведение в изолированном каталоге подтвердило причинную
связь: сборка инцидента перезаписала контрольный JSON при завершении JVM,
исправленная сборка сохранила его побайтно. Дополнительное ревью нашло
обход защиты через явный `write()` после неудачного чтения; он тоже закрыт.
Финальный `ant test jar`: 3063 теста прошли, 0 ошибок, 49 секунд;
журнал `build/performance/tests-explicit-guard.log`. Восстановленный профиль
после этого прогона побайтно совпадает с подготовленным снимком.

подтверждена. Следующий шаг — убрать растеризацию подписей из UI-потока с
проверкой обновления текста, устаревших результатов и освобождения текстур.

на построение покрытий карты и поиск объектов, но недостаточны для назначения
причины. В это же время работают фоновые задачи местности; отдельный кластер
деоптимизаций JIT также не доказывает причину пауз. Паузы GC не превышают

## Фоновая подготовка подписей зон

Конструктор подписи и её обновление больше не растеризуют текст. При видимом
отображении UI снимает значения названия, качества, значков и стиля; отдельный
daemon-поток готовит три изображения. Очередь ограничена 64 запросами, на одну
подпись допускается одна незавершённая задача. Поколение запроса исключает
установку устаревшего изображения после переименования или удаления. Рабочая
задача не держит ссылок на Gob/UI и не читает живые настройки или данные зоны.

Текстуры создаются при приёме готового результата в UI; прежние освобождаются.
Удаление последнего render slot отменяет результат и освобождает текстуры,
но допускает повторное добавление подписи. Окончательный dispose закрывает
запросы. Установка изображения синхронизирована с внешними обновлениями зон,
которые могут приходить от фоновой синхронизации. При ошибке или переполнении
очереди повтор ограничен задержкой, тяжёлая работа не выполняется в вызывающем
потоке. Внешний вид имени, качества и значка проверяется попиксельно против
прежнего алгоритма; тесты также проверяют отмену, очередь, повтор и удаление.

Независимое ревью проверило вызовы удаления в RenderTree и обновлений из
фонового потока. Найденные при проверке гонка pending и отсутствие очистки
при удалении slot исправлены до игрового запуска. Эффект на реальные интервалы
кадров этой версии ещё не измерен.

Финальный изолированный `ant test jar`: 3070 тестов прошли, 0 ошибок, 54 с;
журнал `build/performance/tests-async-area-labels-final.log`. Проверка 192 заметок

## Устранение сна при переходе и повторной подготовки кнопок

Обработка смены участка карты больше не вызывает `Thread.sleep(100)`.
Обычная граница без известного входного портала завершается сразу. Для
известного портала сохраняются вход, домашний контекст и позиция приземления;
поиск выхода выполняется на последующем tick не ранее чем через 100 мс.
Новая граница, reset и отключение отслеживания отменяют ожидающий переход.
Отсутствие ещё не загрузившегося выхода не помечает вход навсегда обработанным.
Время в регрессионных тестах управляется явно, без настоящего ожидания.

Дополнительно обнаружена подтверждённая повторная работа панели действий:

изображения состояний и текстуру. Панель теперь хранит одну кнопку на слот.

или его изображений, а также масштаба пересоздаёт кнопку и освобождает
прежнюю. Удаление назначения и закрытие панели очищают принадлежащие ей
текстуры. Выполнение действий по щелчку и горячей клавише по-прежнему
обращается к текущему менеджеру сценариев/наборов. Это уменьшает постоянную

## Пересборка атласа только при необходимости

Скрытый атлас больше не строит каталог при создании, смене меню и tick.
Первое открытие строит актуальный каталог; изменения меню/наблюдений,
пришедшие пока окно скрыто, объединяются в одно обновление. Повторное
открытие при тех же ревизиях использует готовый результат. Если ресурс
ещё загружается при классификации страницы или чтении её данных, каталог
помечается неполным и видимое окно повторяет попытку через секунду.
Скрытое окно такие повторы не делает. Выбор рецепта сохраняется по ресурсу.

Встроенный справочник теперь разбирается один раз и переиспользуется
между сессиями. Его список и вложенные значения неизменяемы; отдельный
метод разбора произвольного InputStream сохраняет прежнюю независимость.
Первое открытие атласа и первый разбор встроенного справочника всё ещё
синхронны: эти изменения не обещают устранения всех пауз при открытии.
Независимое ревью gate/retry и публикации общего справочника существенных
замечаний не выявило; 15 профильных тестов gate/catalog прошли в изоляции.
Общая проверка сборки будет выполнена вместе с переносом чтения навигации.

## Чтение навигации до захвата UI lock

В конце конструктора NGameUI, который Loader вызывает до входа в монитор UI,
файлы навигации читаются в отдельный временный набор. Он не публикует manager,
не меняет граф и не сохраняет настройки. При attach выполняется прежняя
инициализация manager с миграциями, repair и backfill, затем выставляется
готовность. Для неизменившихся файлов берутся уже прочитанные данные.
Так из-под монитора убирается цикл открытия и чтения файлов, наблюдавшийся
во время 3,5-секундного ожидания. Сам вход всё ещё ждёт загрузку навигации,
но чтение не удерживает блокировку отрисовки.

Набор привязан к миру и абсолютному нормализованному каталогу, используется
один раз и освобождается после передачи. Перечисление при загрузке остаётся
актуальным: новые/изменённые файлы читаются, удалённые не добавляются.
Сравниваются размер, время изменения/создания и fileKey, если он доступен.
На Windows в этом JDK fileKey отсутствует, поэтому все штатные записи и
удаления дополнительно изменяют общее поколение каталога; активная или
промежуточная запись отменяет использование подготовленного набора.
Предварительное чтение не удаляет повреждённые файлы; их обрабатывает
прежний загрузчик. Старая JSON-миграция полностью использует прежний путь.

Намеренное внешнее копирование с сохранением всех времён и размера при
отсутствующем fileKey неотличимо по метаданным. Последовательное сохранение
нескольких файлов, как и ранее, не является единой транзакцией снимка.
Межсессионная запись штатными методами покрыта проверкой поколения.
Восемь профильных тестов предварительного чтения прошли именно на Windows
без пропусков. Независимое ревью существенных новых рисков не выявило.

## Повторное использование кнопок миникарты и владелец проверки карты

## Закрытие сессии без повторной записи неизменённых меток

LabeledMarkService.dispose ранее безусловно строил JSON всех меток и
выполнял атомарную запись с резервной копией после ожидания писателей.
Теперь последний успешно записанный снимок учитывает согласованные
ревизию, путь и идентичности общих значков. Неизменённый корректный
primary-файл версии 2 также образует исходное сохранённое состояние.
Повторная запись при закрытии пропускается только при том же состоянии,
существующем файле, пустых очередях и завершённых фоновых писателях.

Старый формат, восстановление из резервной копии, ошибка записи,
частичная загрузка, повторяющиеся/неканонические ID, изменения меток
и поздняя регистрация значка сохраняют обязательную запись. Явное save
по-прежнему пишет файл. Изменённые метки при закрытии сохраняются
синхронно; ожидания до 2 с/5 с для действующих писателей не изменены.
