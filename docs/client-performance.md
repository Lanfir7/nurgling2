# Профилирование производительности клиента

Для короткой записи Java Flight Recorder нужен JDK с `jcmd` и `jfr` в `PATH`.
Укажите PID именно запущенного клиента; например, его можно найти через `jcmd -l`.
Запускайте из корня проекта:

```powershell
python tools/profile_client.py record --pid 12345 --duration 30 --name travel --max-size-mb 64
python tools/profile_client.py analyze build/performance/client_travel_YYYYMMDDTHHMMSSZ_XXXXXXXX.jfr
```

Для сопоставимого замера после изменений сначала завершите старый клиент обычным
способом, затем соберите диагностическую версию и запустите её:

```powershell
ant jar
python tools/start_profiled_client.py
```

Скрипт создаёт отдельную копию JAR и серверной конфигурации в уникальной
папке `build/performance/*-runtime/`. Работающий клиент не использует
пересобираемый `build/hafen.jar`: следующая сборка не должна менять файлы,
из которых JVM ещё подгружает классы. Не удаляйте папку запуска до выхода
из соответствующего клиента.

Перед запуском скрипт копирует настройки и горячие клавиши вместе с их `.bak`
в подпапку `settings-backup/` нового запуска. Эта копия независима от
вращающегося резервного файла клиента. Восстанавливать её можно только после
закрытия клиента, иначе автосохранение может перезаписать восстановленный файл.
Резервные копии содержат личные данные; не публикуйте папку запуска целиком.

`ant test` запускает тестовую JVM с отдельными AppData, домашним каталогом и
Java Preferences в памяти. При ручном запуске JUnit сохраняйте эту изоляцию:
тестовые объекты настроек и обработчики завершения JVM не должны использовать
каталог игрока. Не запускайте старые сборки тестов на настоящем профиле.

В игре нажмите Esc, переключитесь на английскую раскладку и нажмите Shift+;
(символ `:`). Внизу откроется консоль. Введите `perf start` и нажмите Enter,
чтобы сбросить счётчики перед нужным сценарием. Снова откройте консоль для
следующей команды: `perf stop` останавливает сбор, `perf status` показывает
краткую сводку, `perf export` сохраняет `performance-<время>.csv` в рабочей
папке клиента (при запуске этим скриптом — в корне проекта). Можно указать
новый путь: `perf export build/performance/walking.csv`.

Если игровая консоль недоступна, уже собранные кадры можно забрать снаружи:

```powershell
python tools/export_client_frames.py 12345
```

Нужен JDK с `javac`, `jar`, `java` рядом с `jcmd`. Помощник подключает
одноразовый Java Attach agent, читает снимок метрик активного визуального
цикла и сохраняет новый CSV в `build/performance/`. Он не подменяет классы,
не останавливает игру и не сбрасывает запись. При запрещённой JVM загрузке
агентов команда завершится ошибкой; ограничение не обходится.

В CSV `interval_ms` — интервал между кадрами, `total_ms` включает ожидания;
`tick_ms`, `draw_ms` и `submit_ms` показывают работу CPU, включая подготовку
команд отрисовки, но не измеряют время GPU. Отдельные `sync_wait_ms` и
`limit_wait_ms` помогают отделить ожидание от работы. Сводка рассчитывается
по видимым отрисованным кадрам, исключая фоновый режим и переходные интервалы.
`end_epoch_ms` — время завершения кадра для сопоставления с JFR. Интервалы
считаются по монотонным часам, поэтому смена системного времени их не меняет.
В более ранних диагностических сборках столбец времени отсутствует.

Запись длится 10–300 секунд; имя допускает только латинские буквы, цифры,
`_` и `-`, а лимит сохраняемых данных JFR составляет 16–256 МБ. Каждая запись
получает уникальный файл в `build/performance/`. Файл появляется после окончания
записи. При анализе существующей записи укажите её путь. Инструмент не выводит
переменные среды, свойства JVM и список процессов; соответствующие события
отключены для новых записей этого инструмента. Существующие записи могут содержать
их, поэтому делитесь исходным `.jfr` только после проверки его содержимого.

Отчёт JFR показывает число выборок CPU по потокам и верхним методам стека,
оценочный объём выделений из весов выборок, паузы фаз GC и самые длинные
зафиксированные блокировки монитора и операции ввода-вывода. Число выборок не
равно времени выполнения; спящий или ожидающий поток сам по себе не указывает
на падение FPS. JFR записывает блокировки и операции только при превышении
порогов профиля, поэтому пустой раздел не доказывает их полного отсутствия.
Отдельный раздел ожиданий UI включает `ThreadSleep`, `ThreadPark` и
`JavaMonitorWait`: время начала и первый метод клиента в стеке позволяют
сопоставить паузу с CSV кадров. Долгое ожидание фонового потока не вытесняет
короткую остановку UI из этого раздела.
Захват занятого монитора (`JavaMonitorEnter`) показан отдельно для UI,
с временем начала, адресом блокировки и последним предыдущим владельцем.
Чтобы установить, кто держал монитор во время всей паузы, сопоставляйте
выборки других потоков: previousOwner может быть лишь последним из них.

Для проверки микрофризов повторите одинаковое действие в клиенте с диагностикой,
сохраните отдельные записи до и после изменения и сравните стеки и длительности
пауз. На результат влияют нагрузка системы, прогрев JVM и игровые условия.
Во время измерения не запускайте сборки, тесты или тяжёлый разбор предыдущих
записей. Сопоставляйте один и тот же маршрут с одинаковыми настройками;
замеры после восстановления другого профиля не являются строгим A/B-тестом.
