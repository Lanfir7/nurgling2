# Направление заполнения зоны стокпайла

Дата: 2026-08-30

## Цель

Вернуть последовательное заполнение зоны кучами от выбранной стороны вместо размещения в ближайшем к персонажу свободном месте. Пользователь должен видеть направление у выбранной зоны, менять его через контекстное меню и получать одинаковое значение после перезапуска и на других синхронизированных клиентах.

Одновременно дублирование зоны должно проходить тот же жизненный цикл создания, что и новая зона: получать собственный UUID, сохраняться в локальную БД и отправляться серверной синхронизацией как новая независимая зона.

## Направления и порядок кандидатов

В модель зоны добавляется перечисление `PileFillDirection` с четырьмя значениями:

- `LEFT_TO_RIGHT`: столбцы слева направо, внутри столбца сверху вниз;
- `RIGHT_TO_LEFT`: столбцы справа налево, внутри столбца сверху вниз;
- `TOP_TO_BOTTOM`: строки сверху вниз, внутри строки слева направо;
- `BOTTOM_TO_TOP`: строки снизу вверх, внутри строки слева направо.

`LEFT_TO_RIGHT` является значением по умолчанию. Оно точно повторяет порядок, который использовался до сортировки свободных мест по расстоянию до персонажа: начало в верхнем левом углу, проход сверху вниз и затем переход к следующему столбцу справа.

Отсутствующее, пустое или неизвестное значение при загрузке заменяется на `LEFT_TO_RIGHT`. Старые зоны поэтому сохраняют прежнее поведение без ручной миграции данных пользователем.

## Размещение куч

`PileMaker` получает направление из целевой `NArea` и запрашивает у `Finder` кандидатов в соответствующем стабильном порядке. Сортировка кандидатов по расстоянию до персонажа для создания куч больше не используется.

На каждой итерации выбирается первое геометрически допустимое свободное место в заданном порядке. Следующий кандидат рассматривается только когда текущий действительно занят, не допускает установку или остаётся недоступным после штатной попытки выйти из предыдущего стокпайла.

Сохраняются существующие защитные механизмы:

- шаг сетки и проверка габаритов создаваемой кучи;
- проверка коллизий и фактической возможности размещения;
- выход персонажа из хитбокса предыдущего стокпайла на ближайшую допустимую точку;
- повторное построение пути после выхода;
- переход к следующему кандидату при подтверждённой невозможности использовать текущий.

Это не является системой переупаковки существующих куч. Алгоритм не перемещает уже созданные стокпайлы, а выбирает наиболее раннюю свободную позицию согласно направлению для каждой новой кучи.

## Модель и сериализация

В `NArea` добавляется поле направления со значением `LEFT_TO_RIGHT` по умолчанию. Поле входит в JSON зоны под стабильным ключом `pile_fill_direction`.

Направление относится к `AreaFieldGroup.ROUTING`, потому что изменяет поведение автоматизации, а не геометрию или внешний вид зоны. Изменение направления:

1. обновляет поле выбранной зоны;
2. вызывает `markDirty(ROUTING)`;
3. вызывает стандартный `NConfig.needAreasUpdate()`;
4. проходит обычный цикл локального сохранения и серверной синхронизации.

`AreaSnapshot`, merge и серверный `AreaService` должны включать `pile_fill_direction` в данные группы `ROUTING`. При конфликте применяется существующая политика слияния для этой группы.

## Локальная БД

Локальная `Areas.db` хранит поля зоны в фиксированной схеме, поэтому одной JSON-сериализации недостаточно. Добавляется следующая миграция `AreasDBMigrationManager`:

- новая колонка `areas.pile_fill_direction` строкового типа;
- `NOT NULL` или эквивалентная безопасная обработка `NULL`;
- значение по умолчанию `LEFT_TO_RIGHT`;
- существующие строки получают `LEFT_TO_RIGHT`.

`AreaDBStorage` читает и записывает колонку во всех путях:

- полная загрузка зон;
- загрузка зоны для сравнения;
- вставка;
- обновление;
- восстановление удалённой зоны;
- проверка фактических изменений.

JSON fallback также использует поле `pile_fill_direction` через `NArea.toJson()` и JSON-конструктор.

## Серверная синхронизация

Серверный формат получает `pile_fill_direction` внутри JSON-данных зоны. Отдельная серверная колонка не требуется: существующий сервис уже синхронизирует составные данные зоны через JSON.

Синхронизация обязана обеспечивать:

- отправку локального изменения направления;
- загрузку направления с сервера;
- сохранение направления при автоматическом merge;
- fallback на `LEFT_TO_RIGHT` для записей старого формата;
- независимую синхронизацию дубликата под новым UUID.

## Единый жизненный цикл новой зоны

Создание обычной зоны и создание дубликата используют общий метод инициализации новой зоны. Метод выполняет синхронизационную часть создания в одном месте:

- назначает новый UUID;
- сбрасывает `version`, `baselineVersion` и `baselineSnapshot`;
- сбрасывает `synced`, `lastUpdated` и прочие метаданные прежней серверной записи;
- задаёт новое время локального изменения;
- помечает `GEOMETRY`, `IDENTITY`, `COSMETIC` и `ROUTING` как dirty;
- оставляет зону готовой для стандартного `needAreasUpdate()`.

Обычная новая зона получает направление `LEFT_TO_RIGHT`. Дубликат сначала глубоко копирует пользовательские данные исходной зоны, включая направление, геометрию, цвет, маршрутизацию и специализации, затем проходит общий метод инициализации как новая независимая зона.

Дубликат не наследует UUID, версию, baseline или состояние синхронизации источника. Это устраняет текущую ситуацию, когда копия с `uuid = null`, но с унаследованной версией и пустым набором dirty-групп может быть сочтена неизменённой и не сохраниться.

## Интерфейс выбора

В контекстное flower-меню элемента зоны рядом с действием «Дублировать» добавляется локализованное действие «Выбор направления».

Действие открывает компактный локальный мини-интерфейс в форме креста с четырьмя кнопками:

- `→` выбирает `LEFT_TO_RIGHT`;
- `←` выбирает `RIGHT_TO_LEFT`;
- `↓` выбирает `TOP_TO_BOTTOM`;
- `↑` выбирает `BOTTOM_TO_TOP`.

Текущий выбор должен быть визуально различим. После нажатия мини-интерфейс закрывается, направление меняется немедленно, зона помечается dirty и инициируется стандартное сохранение. Отмена или клик вне меню не изменяют зону.

## Стрелка в зоне

В центре выбранной зоны отображается широкая полупрозрачная стрелка, лежащая в плоскости земли и указывающая направление заполнения. Она использует тот же `PileFillDirection`, что и алгоритм, поэтому визуальное состояние не может расходиться с фактическим порядком.

Стрелка видна только при одновременном выполнении условий:

- окно настроек зон открыто;
- выбрана конкретная зона;
- выбранная зона загружена и имеет доступный центр.

Стрелки остальных зон не отображаются. При смене выбора, изменении направления, изменении геометрии или загрузке другой части зоны оверлей обновляется. При закрытии окна, снятии выбора или уничтожении виртуальной метки оверлей удаляется вместе с ней.

Стрелка является диагностическим UI-оверлеем и не участвует в коллизиях, поиске пути или выборе позиции кучи.

## Обработка ошибок и совместимость

- Неизвестное направление из JSON или БД не ломает загрузку: используется `LEFT_TO_RIGHT`.
- Неуспешное сохранение обрабатывается существующим механизмом повторов и последующего dirty-save; UI не создаёт отдельный путь записи.
- Если зона не загружена, стрелка временно отсутствует, но значение направления сохраняется.
- Дубликат не добавляется как синхронизированный объект до прохождения стандартного сохранения новой зоны.
- Изменение не должно затрагивать правила выбора типа предмета, threshold или массовой отправки в стокпайл.

## Проверки

Автоматические тесты должны покрывать:

1. точный порядок координат для всех четырёх направлений;
2. прежний `LEFT_TO_RIGHT` порядок по умолчанию;
3. отсутствие сортировки по расстоянию до персонажа при создании куч;
4. сохранение шага сетки и пропуск только реально недоступных кандидатов;
5. выход из предыдущего стокпайла без появления лишнего отступа;
6. JSON round-trip направления и fallback для отсутствующего/неизвестного значения;
7. локальную миграцию БД и чтение/запись направления всеми путями `AreaDBStorage`;
8. включение направления в `ROUTING` snapshot/merge и серверный JSON;
9. смену направления через UI с `markDirty(ROUTING)`;
10. видимость стрелки только для выбранной зоны при открытом окне;
11. мгновенное обновление ориентации стрелки;
12. наследование направления дубликатом;
13. новый UUID, нулевой baseline и полный набор dirty-групп у дубликата;
14. прохождение дубликатом того же сохранения и серверной синхронизации, что и новой зоной;
15. полную сборку проекта и существующий регрессионный набор тестов.

## Критерии готовности

- Новые кучи последовательно заполняют зону от выбранной стороны.
- Старые зоны без нового поля ведут себя точно как до сортировки по близости к персонажу.
- Пользователь меняет направление четырьмя стрелками из контекстного меню зоны.
- Широкая стрелка в центре показывает реальное направление только у выбранной зоны и только при открытых настройках.
- Направление переживает перезапуск клиента и синхронизируется между клиентами.
- Дубликат сохраняет направление и пользовательские настройки, но создаётся как новая зона с отдельным UUID и полным циклом синхронизации.
- Исправления выхода из предыдущего стокпайла и безопасного выбора позиции не регрессируют.
